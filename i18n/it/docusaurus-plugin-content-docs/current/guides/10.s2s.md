# Comunicazione Server-to-Server (S2S)

La comunicazione Server-to-Server (S2S) avviene tra il server di Voucherly e il server del merchant al termine di una fase di checkout, per notificare il merchant sull'esito del pagamento.

:::info
Si consiglia di configurare un endpoint S2S sul server del merchant per evitare di perdere l'esito del pagamento nel caso in cui il cliente chiuda il browser prima di essere reindirizzato al `redirectOkUrl` o al `redirectKoUrl` del merchant.
:::

:::warning
Poiché la chiamata S2S viene inviata ogni volta che un utente completa il flusso di checkout per un pagamento, potrebbero verificarsi casi in cui vengono ricevute due richieste. Questo può accadere se il pagamento creato dal merchant è in modalità `Payment`, il Wallet è abilitato e il cliente decide di ricaricare il Wallet durante il processo di pagamento. Voucherly gestisce la ricarica del Wallet come un pagamento separato (come descritto nel caso d'uso [Ricarica Wallet](use-cases/charge-wallet)), collegandolo al pagamento originale tramite il campo `ParentPaymentId` (l'ID del pagamento creato dal merchant) e assegnandogli la modalità `Wallet`.
:::

## Integrazione

L'URL dell'endpoint del merchant deve essere specificato durante la creazione del pagamento tramite la [Create Payment API](/api/webapi/create-payment).

Quando il cliente lascia la pagina di Checkout di Voucherly, indipendentemente dal fatto che il pagamento sia andato a buon fine o meno, Voucherly tenta di contattare il server del merchant prima di reindirizzare il cliente al sito web del merchant.

Il merchant deve configurare un endpoint che accetti una richiesta POST con un corpo JSON contenente un sottoinsieme delle proprietà del pagamento.

### Formato della Richiesta

- **Id** *(string)*  
  Identificativo univoco del pagamento.  
- **Tenant** *(string)*  
  Indica l'ambiente: *live* o *sand*.  
- **Mode** *(string)*  
  Modalità del pagamento: `Payment` o `Wallet`.  
- **ReferenceId** *(string)*  
  Una stringa univoca per riferire il pagamento (ad esempio, ID cliente, ID carrello) per la riconciliazione con i sistemi interni.  
- **MerchantId** *(string)*  
  Identificativo del merchant.  
- **CustomerId** *(string)*  
  ID del cliente per questo pagamento.  
- **TotalAmount** *(long)*  
  Importo totale prima degli sconti.  
- **DiscountAmount** *(long)*  
  Importo scontato.  
- **FinalAmount** *(long)*  
  Importo finale, calcolato come `TotalAmount` - `DiscountAmount`.  
- **PaidAmount** *(long)*  
  Importo effettivamente pagato.  
- **PaidVoucherAmount** *(long)*  
  Porzione del pagamento effettuata con voucher.  
- **Amount** *(long)*  
  Importo netto del pagamento.  
- **Status** *(string)*  
  Stato attuale del pagamento: `Requested`, `Paid`, `Confirmed`, `Refunded`, `Cancelled`, `Voided` o `Expired`.

:::info
Poiché l'endpoint S2S del merchant non richiede alcuna configurazione di autenticazione, si consiglia di utilizzare l'API [Get Payment](/api/webapi/get-payment) per verificare che la richiesta provenga da Voucherly. Questa API fornisce tutte le informazioni necessarie sul pagamento.
:::

#### Risposta
Il server del merchant deve rispondere con un codice di stato HTTP `200 OK` e un corpo JSON nel seguente formato:

- **Ok** *(bool)*  
  Indica se la richiesta S2S è stata elaborata correttamente dal server del merchant.  
- **OrderId** *(string?)*  
  Identificativo univoco dell'ordine nei sistemi del merchant.  

```json [Risposta S2S Attesa]
{
    "ok": true,
    "orderId": "eb8f57f8-241b-4142-b7b0-d308d724541a"
}
```

:::warning
Se il server del merchant risponde con un codice di stato HTTP diverso da `2xx` o se il campo `Ok` nel corpo della risposta è `false`, Voucherly tenterà di ripetere la chiamata fino a tre volte. Se il problema persiste, il pagamento verrà annullato e tutte le transazioni saranno rimborsate.
:::
