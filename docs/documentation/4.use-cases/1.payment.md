# Accept Payment
Accepting a payment allow merchant to initialize a new payment instance for a customer and manage the result.

Below will show the classic payment flow and steps to allow a quick and easy integration on the merchant website.

## Payment lifecycle
1. When customer is ready to complete their purchase, merchant website has to create a new Payment throw the [Create Payment Api](/api/webapi/create-payment), setting `mode` to `Payment`.

2. In the response there is the url of Voucherly checkout page to redirect to.

3. Customer can pay with voucher payment gateway and/or a non voucher payment gateway and complete the payment.

4. After completing the payment, if the `S2SUrl` field was populated when called the [Create Payment Api](/api/webapi/create-payment), a [Server to Server](/docs/s2s) will be sent with the result to the specified url. Then customer will be redirect to the merchant website url, specified in [Create Payment Api](/api/webapi/create-payment) request.

5. Last step is to call the [Confirm Payment Api](/api/webapi/confirm-payment), thus confirming all paid but not yet confirmed transactions. Typically, payment confirmation takes place on delivery. Note that this step has to be done only if [Auto Confirm](/docs/resources/payments#auto-confirm) has not been enabled from the Dashboard.

## Restrict available payment gateways
Merchant website can choose at runtime which payment gateways can be used for every payment. In the [Create Payment Api](/api/webapi/create-payment) you can specify an array of payment gateway IDs (see [here](/docs/resources/payment-gateways) for a full list).

If you don't need this feature, please leave `PaymentGateways` field empty and enable/disable them from the Dashboard.

## Wallet charge inside payment
On the Voucherly Checkout page for a payment with Wallet active, customer has the possibility to charge the wallet credit, to be used in the current or future payments.

This is completely handled by Voucherly and doesn't required any specific integration by the merchant. 

If a wallet charge occurs within the payment flow, a new payment object will be created, with `Mode` to `Wallet` and with `ParentPaymentId` the ID of the Payment from which the wallet charge flow originated.

## Complete or Refund a payment
A payment may consist of several transactions made on different payment gateways, some successful and others not.

As described in [this](/docs/resources/payments) in-depth look at how transactions works, once the customer has completed payment and been redirected to the merchant's website, successful transactions can be in status `PAID` or `CONFIRMED`. This depends on various factors such us the type of payment gateway or if [Auto Confirm](/docs/resources/payments#auto-confirm) is enabled. 

:::warning
Successful transactions made at a voucher payment gateway will go directly to `CONFIRMED` status.
:::

You always need to confirm or refund the payment. If you leave a payment in `PAID` status, the behaviour will depend on the configuration of the payment gateway and funds could return to customer. Always confirm a successful payment, for example when the order is prepared or shipped.


## Quick guide
Let's see a little more in detail a simple example of how to integrate the payment flow from scratch.

### 1. Create Payment
:::info
See [Create Payment Api](/api/webapi/create-payment) for all functionality and more details. 
:::

When the customer is ready to complete the purchase, the merchant's website must make an HTTP call to [Create Payment Api](/api/webapi/create-payment).

In the request remember to specify `mode` as `Payment`, customer data and/or customer id if it's not his first payment, the `redirectSuccessUrl` and `redirectErrorUrl` where customer will be redirected when finishes on the Voucherly checkout page. `lines` are the articles the customer is finalising the purchase of. For each item, `isFood` needs to determine the products payable with vouchers. The total payment amount is calculated by adding for each payment line `(unitAmount - unitDiscountAmount) * quantity - discountAmount` minus `discount`.

The `referenceId` is an optional field and allows you to add a custom identifier (such as a cart ID, order Id, ...) in order to reconcile the Payment with your internal system. 

It is recommended to set up an endpoint that will be called from the Voucherly server to server to merchant's website of the outcome of a payment. The endpoint url should be passed into the `s2sUrl` field.

:::warning
Merchant has to save the customer id generated by Voucherly on the first payment. For the future payments, it will only be necessary to fill the `CustomerId`, while customer information (firstname, lastname, email, ...) only if you want to update that data.
:::

### 2. Setup a checkout callback page
When customer completes the payment on the Voucherly Checkout page, he will be redirect to the urls specified in the [Create Payment Api](/api/payments/create_payment) request: if payment was successfully completed, customer will be redirect to `redirectSuccessUrl`, otherwise to the `redirectErrorUrl`.

You have to set up two routes on merchant website that handle the payment result and accept the query string parameters that will be sent:
  - **success** Can be `OK` if payment success, otherwise `KO`.
  - **status** Is the payment status.
  - **paymentId** The id of the payment, in the format `sbpay-XXXXXXXXXXX`.
  - **amount** The paid amount in cents.
  - **voucherAmount** The paid amount with voucher in cents.
  - **walletAmount** The paid amount with wallet in cents.
  - **transactions** The number of transactions.
  - **customerId** The Voucherly identifier of the customer in the format `cs-XXXXXXXXXXX`. Has to be stored in merchant website for future payments.
  - **customerFirstName** Customer firstname.
  - **customerLastName** Customer lastname.
  - **customerEmail** Customer email.
  - **referenceId** Merchant reference id sent when created payment.

### 3. Setup server to server endpoint (optional)
It is recommended to define an endpoint that will be contacted by Voucherly's S2S to notify the result of a payment before the redirect to the merchant's site. See [here](s2s) for more details on how to implement a S2S endpoint and his behaviour.

:::warning
As described in the [Server to Server section](/docs/s2s), pay attention that if your endpoint does not respond correctly to s2s, the payment will be cancelled and the amounts refunded.
:::

### 4. Confirm payment
:::info
See [Confirm Payment Api](/api/payments/confirm-payment) for all functionality and more details. 
:::

:::warning
If you prefer not to process a two-step payment but want transactions to be confirmed immediately, ignore this point and enable Auto Confirm from Dashboard.
:::

The payment confirmation usually occcurs when the order is accepted by the merchant. It's sufficient to call the [Confirm Payment Api](/api/webapi/confirm-payment).

If the order cannot be delivered or customer cancels the order before the shipping, you can call the [Refund Payment Api](/api/webapi/refund-payment). Automatically Voucherly cancels transations in `PAID` status and refunds those in `CONFIRMED` status.
