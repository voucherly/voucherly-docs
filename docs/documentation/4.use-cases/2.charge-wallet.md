# Charge wallet
As already seen, customer can charge his wallet during the payment. Voucherly offers the possibility to integrate a dedicated flow only for charging the wallet.

:::warning
This use case is available only if wallet is enabled from the Dashboard.
:::

## Charge wallet lifecycle
The flow is the same as for payment, with the only difference being the parameters to pass to the [Create Payment Api](/api/webapi/create-payment).

1. When customer want to charge his wallet, you have to create new Payment throw the [Create Payment Api](/api/webapi/create-payment), setting `mode` to `Wallet`.
    - You can pass directly an amount to be charged on the wallet filling a single `line` with that amount and quantity to 1.
    - If you don't pass any `line`, Voucherly will ask customer the amount.

2. In the response there is the url of Voucherly checkout page to redirect to.

3. Customer can pay with voucher payment gateway and/or a non voucher payment gateway and complete the payment.

4. After completing the payment, if the `S2SUrl` field was populated when called the [Create Payment Api](/api/webapi/create-payment), a [Server to Server](/documentation/s2s) will be sent with the result to the specified url. Then customer will be redirect to the merchant website url, specified in [Create Payment Api](/api/webapi/create-payment) request.

:::warning
When customer exit the checkout page, transaction are alredy in `CONFIRMED` state. You don't have to confirm them via api and you cannot refund a wallet charge.
:::

## Quick guide
Let's see a little more in detail a simple example of how to integrate the charge wallet flow from scratch.

### 1. Create Payment
:::info
See [Create Payment Api](/api/webapi/create-payment) for all functionality and more details. 
:::

When the customer is ready to charge his wallet, the merchant's site must make an HTTP call to [Create Payment Api](/api/webapi/create-payment).

In the request remember to specify `mode` as `Wallet`, customer data and/or customer id if it's not his first time, the `redirectSuccessUrl` and `redirectErrorUrl` where customer will be redirected when finishes on the Voucherly checkout page. 
If you want to delegate to Vuocherly the request to the customer of the amount he intends to reload, do not pass any `lines`. Otherwise populate a single payment line with unit quantity and the amount to be recharged

The `referenceId` is an optional field and allow merchant to add a custom identifier (such as a cart ID, order Id, ...) in order to reconcile the Payment with your internal system. 

It is recommended to set up an endpoint that will be called from the Voucherly server to server to merchant's website of the outcome of a payment. The endpoint url should be passed into the `s2sUrl` field.

### 2. Setup a checkout callback page
When customer completes the wallet charge on the Voucherly Checkout page, he will be redirect to the urls specified in the [Create Payment Api](/api/webapi/create-payment) request: if payment was successfully completed, user will be redirect to `redirectSuccessUrl`, otherwise to the `redirectErrorUrl`.

The merchant must set up two routes on his website that handle the payment result and accept the query string parameters that will be sent:
  - **success** Can be `OK` if payment success, otherwise `KO`.
  - **status** Is the payment status.
  - **paymentId** The id of the payment, in the format `sbpay-XXXXXXXXXXX`.
  - **amount** The paid amount in cents.
  - **voucherAmount** The paid amount with voucher in cents.
  - **walletAmount** The paid amount with wallet in cents.
  - **transactions** The number of transactions.
  - **customerId** The Voucherly identifier of the customer in the format `cs-XXXXXXXXXXX`. Has to be stored in merchant website for future payments.
  - **customerFirstName** Customer firstname.
  - **customerLastName** Customer lastname.
  - **customerEmail** Customer email.
  - **referenceId** Merchant reference id sent when created payment.

### 3. Setup server to server endpoint (optional)
It is recommended to define an endpoint that will be contacted by Voucherly's S2S to notify the result of a payment before the redirect to the merchant's site. See [here](s2s) for more details on how to implement a S2S endpoint and his behaviour.

:::warning
As described in the [Server to Server section](s2s), pay attention that if your endpoint does not respond correctly to s2s, the payment will be cancelled and the amounts refunded.
:::
